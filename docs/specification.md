# Career Compass 仕様

エンジニア転職で年収 1000 万円到達を目標にしたキャリア管理アプリの仕様。

セットアップ手順は [../README.md](../README.md)、テーブル定義の実体は
`supabase/migrations/` を参照。

## 1. 目的

「年収 1000 万円」という単一の目標に対して、次の 3 つを 1 か所で回せるようにする。

1. **現在地の言語化** — スキル・プロジェクト・成果を、書類にそのまま使える粒度で貯める
2. **条件の明文化** — 業務内容の希望と、業務内容以外（年収・働き方・福利厚生）の希望を分けて持ち、
   応募先ごとに機械的に突き合わせる
3. **書類の自動生成** — 貯めた情報から履歴書・職務経歴書・スキルシートを生成する

## 2. 画面構成

| タブ ID | 画面 | 主な操作 |
|---------|------|---------|

| `skills` | スキル | スキルの追加・編集・削除 |
| `experience` | 職歴・案件 | 職歴とプロジェクトの追加・編集・削除（サブタブ） |
| `education` | 学歴・資格 | 学歴と資格の追加・編集・削除 |
| `highlights` | 自己PR | 文章ブロックの編集、下書き自動生成 |
| `preferences` | 希望条件 | 業務内容 / 業務内容以外 / 福利厚生 / みなし残業 / 優先順位の編集 |

## 3. ドメインロジック

すべて `src/lib/` の純粋関数として実装し、単体テストを持つ。
基準日（`now` / `asOf`）は引数で受け取り、関数内で `new Date()` を既定値にする。

### 3.1 年収ギャップ（`compensation.ts`）

| 出力 | 定義 |
|------|------|
| `gapYen` | `max(0, 目標年収 − 現年収)` |
| `achievementRate` | `現年収 / 目標年収`（現年収未登録なら `null`） |
| `requiredRaiseRate` | `gapYen / 現年収` |
| `jobChangesConservative` | 1 回 +15% で目標に届くまでの最小回数 |
| `jobChangesAggressive` | 1 回 +30% で目標に届くまでの最小回数 |

必要な転職回数は `現年収 × (1 + 上げ幅)^n ≧ 目標年収` を満たす最小の整数 `n`。

パイプライン集計（`summarizePipeline`）は、選考が動いている応募
（`applied` 〜 `offer`）のみを対象に、提示レンジ上限の最高値・中央値、
目標年収に届く求人数を数える。オファー額はステータスに関係なく最高額を拾う。

### 3.2 1000 万円レンジ到達力（`marketValue.ts`）

高年収帯の求人で共通して見られる観点を 6 軸に分解し、0〜100 で採点する。
総合スコアは重み付き平均。

| 軸 | 重み | 満点条件 |
|----|------|---------|
| コアスキルの深さ | 20 | レベル4以上が 3 件、レベル5 が 1 件、最長経験 5 年 |
| 高単価ドメインのカバー | 20 | 定義済みドメインのうち 3 つ以上をカバー |
| リード / 裁量の実績 | 15 | リード相当の役割 + PM/PL 工程 + チーム規模 8 名以上 |
| 成果の定量化 | 20 | 全プロジェクトに定量成果（または数値を含む成果）がある |
| 外部から見える実績 | 10 | 公開リンク 4 件 + 資格 1 件以上 |
| 主力スキルの鮮度 | 15 | 主力スキルすべてが直近 2 年以内に使用されている |

高単価ドメインは `HIGH_VALUE_DOMAINS` に定義したキーワードを、スキル名・備考・
プロジェクトの技術スタック・役割・施策・成果の文字列から検索して判定する。

各軸は満点でない場合に打ち手（`advice`）を返し、`(100 − スコア) × 重み ÷ 100` を
影響度としてソートしたものをダッシュボードに出す。

### 3.3 マッチ度（`matching.ts`）

応募先 1 件と希望条件を突き合わせ、0〜100 のスコアと未充足条件を返す。

| 要素 | 重み | 判定 |
|------|------|------|
| 年収 | 35 | 理想額で 100、最低ラインで 60、下回ると 0 に向けて減衰 |
| 技術スタック | 20 | 希望技術のうち一致した割合 |
| 職種 | 15 | 希望職種に一致すれば 100、しなければ 30 |
| 業界 | 10 | 希望業界に一致すれば 100、しなければ 40 |
| 働き方（リモート） | 12 | 完全一致 100 / 近い 60 / 不一致 20 |
| 勤務地 | 8 | 希望地に一致 100 / フルリモートなら 80 / それ以外 0 |
| 福利厚生 | 10 | 希望福利厚生（マスタコード）のうち一致した割合 |
| みなし残業 | 10 | なし 100 / 許容上限内 70〜100 / 上限超過 0〜60 / 受け入れ不可 0 |

判定材料が無い要素（希望が未登録、求人情報が未入力）はスコア計算から除外する。
提示年収は「実オファー → レンジ上限 → レンジ下限」の優先順で採用する。

未充足条件として返すもの:

- 絶対条件（`mustHaveConditions`）の語が求人情報のどこにも現れない
- 提示年収が `incomeFloor` を下回る
- 避けたい技術（`avoidTechStack`）が求人の技術スタックに含まれる
- みなし残業なし希望（`allowFixedOvertime` = false）なのに求人が「あり」
- みなし残業時間が許容上限（`maxFixedOvertimeHours`）を超える
- 超過分の別途支給が必須（`requireOvertimePayBeyondFixed`）なのに未確認

### 3.5 福利厚生・みなし残業のマスタ（`lib/masters/`）

福利厚生は求人票でよく見る一般的な項目をコード化して持つ（`BenefitCode`）。
自由記述だけだと「住宅手当 / 家賃補助」のような表記ゆれでマッチ度が当たらないため、
選択式のマスタに寄せる。マスタに無い項目は従来どおり自由記述で保持する。

| ファイル | 内容 |
|---------|------|
| `masters/benefits.ts` | 福利厚生マスタ（コード・ラベル・分類・別名）と、自由記述 → コードの正規化 |
| `masters/fixedOvertime.ts` | みなし残業の区分ラベルと採点・説明文の生成 |

- 分類は 報酬・手当 / 働き方 / 休暇 / 学習・成長 / 生活・健康 の 5 つ。
- `toBenefitCode` はラベル・別名との一致（完全一致 → 部分一致）でコードに寄せる。
  既存の自由記述データはこの正規化で比較できるため、DB のデータ移行は行わない。
- `mergeBenefitKeys` はマスタ選択と自由記述をまとめ、重複を除いた比較用キーを返す。
- コード一覧の正は `types/career.ts` の `BenefitCode`。DB 側は `text[]` で持ち、
  項目を増やしても DB の制約変更が要らないようにしている。

みなし残業は「有無・時間数（月）・固定残業代（円）・超過分の別途支給」を項目として持つ。
提示年収が同じでも、みなし残業 45 時間込みかどうかで実質の条件は大きく変わるため、
自由記述ではなく構造化して採点に使う。許容上限が未設定の場合は一般的な目安
（20 時間以内 / 45 時間以内）で採点する。

### 3.4 書類の充足度（`completeness.ts`）

書類種別ごとに必要項目を定義し、必須項目の充足率と未入力項目（+ 遷移先タブ）を返す。
ダッシュボードでは 3 種別を合算し、重複するラベルは 1 件にまとめる。

## 4. 書類生成（`lib/documents/`）

| 種別 | 構成 |
|------|------|
| 履歴書 (`resume`) | 基本情報 → 学歴・職歴（年表）→ 免許・資格 → 志望の動機・自己PR → 本人希望記入欄 |
| 職務経歴書 (`career_history`) | 職務要約 → 活かせる経験・知識・技術 → 職務経歴（会社 → プロジェクト）→ 保有スキル → 資格 → 自己PR → キャリアプラン |
| スキルシート (`skill_sheet`) | 技術スキル（分類別の表）→ 担当案件一覧 |

### 出力形式

生成の中間表現は Markdown。そこから以下に変換する。

- **Markdown**: コピー / `.md` ダウンロード
- **HTML**: `buildPrintableHtml` で A4 印刷用 CSS 付きの完全な HTML を組み立て、
  `.html` ダウンロードまたは別ウィンドウで印刷（ブラウザの「PDF に保存」で PDF 化）

Markdown → HTML 変換は依存を増やさないため自前実装（見出し・表・箇条書き・引用・強調のみ）。
入力は必ず HTML エスケープし、`<br>` と `**強調**` だけを復元する。

### 年表欄の生成規則（履歴書）

- 学歴: 入学行と卒業行の 2 行。卒業行の文言は `status`（卒業 / 中退 / 在学中）を使う
- 職歴: 入社行と退職行。正社員以外は入社行に雇用形態を括弧書きする
- 在籍中（`ended_on` が NULL）の会社があれば、末尾に「現在に至る」を追加する
- 最終行は「以上」

### 本人希望記入欄

希望条件から機械的に文章化する。希望職種・希望年収・希望勤務地・勤務形態・
絶対条件を並べ、末尾に「上記以外は貴社規定に従います。」を付ける。
希望条件が未登録、または並べる項目が 1 つも無い場合は「貴社規定に従います。」のみ。

### 下書き生成（`drafts.ts`）

登録済みデータから叩き台を作る。保存はユーザーが編集してから行う。

| 種別 | 構成 |
|------|------|
| 職務要約 | 経験年数 + 主力技術 → 直近プロジェクトの役割・担当 → 定量成果 → リード経験 |
| 自己PR | 【強み】→【実績】（課題 → 施策 → 成果）×最大 2 件 →【再現性】 |
| 志望動機 | 応募先の業界 → 活かせる経験 → 転職理由 → キャリアプラン |
| 年収交渉 | 希望額と現年収 → 定量成果の列挙 → 再現性 → 想定レンジの逆質問 |

## 5. データフロー

```
画面 → careerStore（Zustand）→ Supabase（PostgREST）
                ↑
        toCamelCase / toSnakeCase
```

- 取得は `fetchXxx`、保存は `saveXxx`（upsert）、削除は `deleteXxx`。
- ミューテーション後は**変更したリソースの `fetchXxx` だけ**を呼ぶ。全件再取得の関数は持たない。
- 初回ロードのみ `App.tsx` で各 `fetchXxx` を `Promise.all` でまとめて呼ぶ。
- プロフィールと希望条件はユーザーごとに 1 行で、`user_id` を `onConflict` に指定して upsert する。
- エラーは `describeSupabaseError` で文字列化し、ストアの `error` に載せて画面上部に出す。

### 入力途中データ（下書き）

`App.tsx` はアクティブなタブのパネルだけを描画するため、タブを切り替えると
パネルがアンマウントされ、ローカル state のフォーム内容が失われる。
これを避けるため、フォームの値は `draftStore`（`src/stores/draftStore.ts`）に逃がす。

- 各パネルは `useState` の代わりに `useDraftState(key, createInitial)` を使う。
  戻り値は `[value, setValue, hasDraft]` で、`useState` と同じ感覚で書ける。
- キーは `<パネル>:<フォーム名>`（例: `applications:form` / `applications:editingId`）。
- 永続化先は sessionStorage。タブ切り替えに加えてリロードにも耐える。
- 下書きは「持ち主（ユーザー ID）」に紐づき、ログアウト・ユーザー切り替えで破棄する
  （`setOwner` を `App.tsx` の初回ロード effect で呼ぶ）。
- プロフィール・希望条件のように取得値でフォームを初期化するパネルは、
  `hasDraft` が真のあいだサーバー取得値で上書きしない（編集中の内容を優先する）。

## 6. テーブル

| テーブル | 内容 | ID プレフィックス |
|---------|------|------------------|
| `career_profiles` | 基本情報・現年収・目標年収・公開リンク（1 ユーザー 1 行） | `prof_` |
| `career_skills` | 保有スキル | `skill_` |
| `career_experiences` | 職歴（会社単位） | `exp_` |
| `career_projects` | 経験プロジェクト（課題・施策・成果） | `proj_` |
| `career_educations` | 学歴 | `edu_` |
| `career_certifications` | 資格・免許 | `cert_` |
| `career_highlights` | 職務要約・自己PR・志望動機など | `pr_` |
| `career_preferences` | 希望条件・福利厚生の希望・みなし残業の許容範囲（1 ユーザー 1 行） | `pref_` |
| `career_applications` | 応募・選考管理（福利厚生・みなし残業の提示条件を含む） | `app_` |
| `career_documents` | 生成書類のスナップショット | `doc_` |

全テーブルで RLS を有効化し、`auth.uid() = user_id` の行のみ参照・更新できる。
`career_projects.experience_id` と `career_documents.application_id` は
`ON DELETE SET NULL`（親を消しても記録は残す）。

## 7. テスト観点

`src/lib/__tests__/`（純粋関数）と `src/stores/__tests__/`（ストア）に単体テストを置く。

- **compensation**: 到達済み / 未登録 / 境界（ちょうど到達する上げ幅）で転職回数が正しいか
- **marketValue**: 空データで 0 点、定量成果なしで該当軸が 0、鮮度 2 年境界
- **matching**: 判定材料なしの除外、最低ライン割れ、避けたい技術、絶対条件の欠落、
  福利厚生の表記ゆれ吸収、みなし残業の上限超過・受け入れ不可
- **masters**: 福利厚生コードの一意性、自由記述 → コードの正規化、みなし残業の採点境界
- **completeness**: 種別ごとの必須項目、重複ラベルの一意化
- **documents**: 満年齢の誕生日前後、在職中の「現在に至る」、主力プロジェクトの並び順、
  HTML エスケープ（`<script>` が通らないこと）
- **drafts**: 空データでも文章として成立すること
- **draftStore / useDraftState**: 下書きの保存・破棄・持ち主の切り替え、
  アンマウント → 再マウント（タブ切り替え）で入力内容が残ること
